# 每配置阶段计时

运行现有 `run_pipeline.py`（包括GUI调用的81组、L9、单配置模式）或交互式 `main.py` 时自动启用。启动参数不变。新增依赖仅为Python标准库。

输出：`results/timing/<运行时间_唯一标识>/config_timing.csv` 与 `config_timing.json`。CSV使用UTF-8 BOM，可直接用Excel打开；每次运行新建目录，保留历史记录。

CSV的前八列依次为：配置ID、编译秒数、准备与初始化秒数、验证与测量秒数、结果处理秒数、配置总耗时秒数、是否成功、中断或异常备注。附加运行ID、实验序号、状态、当前阶段、开始与结束时间，方便追踪中断。

配置ID使用稳定的 `A3-B2-C2-D1` 形式。实验序号保留原脚本编号，不改OM和日志文件名；L9的序号与全81组的序号不应混为同一配置。

## 计时边界

- 编译：一次完整 `run_atc` 调用，包括编译命令构造、ATC进程及编译日志保存。
- 准备与初始化：本配置流程准备、模型同步/上传、输入生成及上传、每次本地ONNX会话创建、远端输出目录准备、监控启动等。上传重试及等待累计到相应操作所在阶段。
- 验证与测量：本地ONNX `session.run` 和远端msame命令调用的墙钟时间，包含验证推理和性能测试。远端命令是不可进一步拆分的整体，因此包含SSH等待、msame内部ACL初始化/模型加载/推理/退出时间；不将其误称为纯设备推理时间。
- 结果处理：输出下载和解析、余弦相似度计算、统计汇总、性能监控停止及日志保存、指标整理和 `results.json` 的写入。零星配置流程开销由当时激活的阶段承担。
- 配置总耗时：从配置计时器创建到该配置结果写入和清理完成，使用 `time.perf_counter()` 单调时钟。四阶段互斥、可多次进入并累计，其和等于配置总耗时（CSV六位小数可能有微小舍入差异）。不包括最后计时表自身的序列化和落盘，也不包括配置之外的公共步骤。

所有配置共用的首次SSH连接、模块导入、GUI中的ONNX转换/容器复制，以及所有配置完成后的正交分析和算法比较不归入单个配置。计时中途检查点写入会带来少量本地开销，计入当前阶段。

原推理次数、随机输入种子、均值/P95/P99计算、CRITIC/TOPSIS评分均未修改。计时字段独立保存，不作为性能评分指标。`run_supplementary.py` 尚未添加配置级计时入口；本次覆盖主实验的两个入口。

## 成功、异常与中断

- “是”表示编译、验证、测量、结果保存正常完成并获得有效数值。余弦相似度是否满足论文阈值仍由原evaluator判断；执行成功不等于可行性通过。
- 编译失败、验证异常、测量失败、监控或结果保存失败会记为“否”，备注说明原因。验证失败时仍按原主流程尝试性能测试，但不会把该配置计为全部成功。
- Ctrl+C（SIGINT）及发给Python实验进程的SIGTERM会尝试保存已耗时、阶段和中断备注，然后退出。处理不会吞掉中断。
- 每配置开始、编译和验证/测量前有落盘检查点。断电、SIGKILL或强制结束解释器无法执行最终保存；最后一行将停留在 `running`、成功栏为空，耗时仅到最后检查点。不能将其当作完整总耗时或成功实验。
- GUI原有停止按钮不等价于给容器内Python发送终止信号，本次未改其停止机制；远端msame或ATC子进程是否终止也不能仅由本地中断记录证明。
- 本地CSV/JSON使用临时文件加原子替换。若磁盘不可写或空间耗尽，会显式报错；该故障本身不能保证仍能写入同一磁盘。

GUI实际执行容器内 `/home/AscendWork/auto_tune2.0/run_pipeline.py`。使用此修改时需将修改后的相关Python文件一并同步到该目录；只修改Windows副本不会自动替换容器代码。已启动的旧Python进程不会因文件修改而自动启用计时。
